# EP05 多仓协同操作

> 目标：把 IDEA 的多 root 能力（同步分支、一次提交多仓、统一推送与更新）做成 GitSpace 的核心差异，并补齐 MRD 已承诺的推送确认与分支一致性。

| 项 | 说明 |
|---|---|
| 优先级分布 | P0 3 项；P1（待评审） 7 项；P1（待评审） 1 项 |
| 人周（粗估） | P0 阶段（M1–M3） 3；P1 阶段（M4 首批） 14；P1 阶段（M4 后期） 1；合计 18 |
| 依赖 | 现有 `BatchSyncModel`（排队 / 执行 / 成功 / 跳过 / 失败、取消、重试、并发 4）；EP07 冲突流程；EP08 Gerrit 推送 |
| 关联 | MRD 10.2-B、10.4-9 / 13、10.6 流程四、§11 场景二与场景五；[调研 §2.1](./research-fork-idea.md) |

## 1. 现状

- 批量只有 fetch / pull（ff-only 或 merge）/ push 三个动作，执行前没有预检汇总，也没有推送确认弹窗（代码中未找到相应对话框）。MRD 10.4-13 要求确认弹窗展示的仓库与提交数与实际一致。
- 多仓状态表显示每仓分支，但不判断分支是否一致；MRD §11 场景二要求一屏看出「哪些分支不一致」。
- 分支、合并、stash、tag 都只作用于当前选中的一个仓库。
- push 固定执行 `git push`，只能推送已配置上游的当前分支；新分支无法从界面首推。

## 2. 对标参考

- IDEA：同步分支控制（所有 root 同时 checkout / merge / delete，部分失败建议回滚，单仓切换时提示 Branches have diverged）；Push Commits 对话框列出所有仓与各自待推送提交，可逐仓或一次改目标，Push tags 两档；Push Rejected 可「Update all repositories」；Update Project 一次 fetch 全部 root 并按同一策略合入，Update Info 汇总新提交；一次 Commit 可以覆盖多个 root。
- Fork：一次推送多个分支；Pull / Push 按钮显示 ahead / behind；lean branching 同步时自动 stash 并恢复。Fork 没有跨仓能力，以上每个能力在 Fork 中都是单仓的。

## 4. 交互规格

### 4.1 统一流程与状态（F01）

所有多仓动作（同步分支、推送、更新、跨仓 tag、跨仓 stash、批量 cherry-pick、自定义命令批量执行）都走同一个面板：

```text
选择仓库 -> 预检（只读命令） -> 确认（将执行 N 仓 / 跳过 M 仓及原因） -> 并发执行 -> 逐仓结果 -> 重试失败项 / 回滚成功项
```

| 状态 | 含义 | 可执行动作 |
|---|---|---|
| 将执行 | 预检通过 | 取消勾选 |
| 跳过 | 预检不通过，原因写明（有未提交改动、分支已存在、无上游、合并进行中、鉴权失败等） | 查看原因、单独处理 |
| 排队 / 执行中 | 受并发度控制（默认 4，可调 1 至 8） | 取消（运行中的进程终止，已完成的保留） |
| 成功 | 返回码 0 | 回滚（动作支持时） |
| 失败 | 原样展示 git stderr | 重试、打开该仓、复制命令 |
| 已回滚 | 已恢复到操作前的分支 / 指针 | 无 |

- 执行前为每个仓记录「操作前快照」：当前分支名、HEAD SHA、相关分支的 SHA，写入 JSONL 操作日志，回滚只依赖这份记录。
- 预检只用只读命令（`status`、`rev-parse`、`for-each-ref`、`rev-list --count`、`ls-remote`）。

### 4.2 推送确认（F02）与多仓 Push 对话框（F05）

```text
+-- 推送 3 个仓库 -----------------------------------------------------------+
| v GdThread        feature/TASK-123456 -> origin/feature/TASK-123456   2 提交 |
|      a1b2c3d  [TASK-123456] 话题卡曝光埋点修正                              |
|      d4e5f6a  [TASK-123456] 补充单测                                        |
| > GdFeedSupports  master -> refs/for/master（Gerrit 评审）            1 提交 |
| > GdHome          feature/TASK-123456 -> 新建 origin/feature/TASK-123456     |
+----------------------------------------------------------------------------+
| 推送 tag  (*) 不推送   ( ) 当前分支相关 --follow-tags   ( ) 全部 --tags      |
| [编辑全部目标]                                   [取消]   [推送 3 仓 ⌘↩]    |
+----------------------------------------------------------------------------+
```

- F02（P0）只需要顶层三行：仓库、本地分支 → 目标、提交数；F05 增加展开查看提交与文件、改目标、push tags。
- 目标可改为新远端分支，首推时执行 `git push -u <remote> <branch>`，确认框写明「将在远端新建分支」。
- Gerrit 仓目标默认 `refs/for/<上游分支>`，规则见 EP08。
- 永不提供 force，也不提供 `--force-with-lease`（MRD 10.2-G）。
- 被拒（非快进）：结果行显示「远端有新提交」，提供「更新这些仓后重推」，可选 ff-only / merge / rebase，复用 F07 的更新流程，更新成功后再推。

### 4.3 分支一致性（F03）

- 「基准分支」默认取多数仓当前所在分支；可在工作区设置中固定（例如 `release/22.14`）。
- 多仓状态表顶部显示：「12 个仓不在 release/22.14 上 [只看这些仓] [同步切换...]」，后者打开 F04。
- 侧栏工作区卡片显示一致性小结：「分支一致 40 / 52」。

### 4.4 同步分支操作（F04）

入口：多仓状态表多选后右键；分支一致性提示条；命令面板「在选中仓库新建分支」。

```text
+-- 同步分支操作 -----------------------------------------------+
| 动作      (*) 新建并切换   ( ) 切换   ( ) 删除               |
| 分支名    [feature/TASK-123456-topic-card                ]   |
| 起点      (*) 各仓当前 HEAD   ( ) 指定 [origin/master    v]  |
| 有改动时  (*) 跳过该仓   ( ) 先 stash，执行后恢复             |
+--------------------------------------------------------------+
| [x] GdThread        master       将执行                      |
| [x] GdFeedSupports  master       将执行                      |
| [x] GdHome          master  *3   跳过：有未提交改动           |
| [ ] GdIM            dev          跳过：分支已存在             |
+--------------------------------------------------------------+
| 将执行 2 仓，跳过 2 仓                [取消]   [执行 ⌘↩]      |
+--------------------------------------------------------------+
```

| 动作 | 预检 | 每仓执行 | 回滚 |
|---|---|---|---|
| 新建并切换 | 分支不存在；起点 ref 存在；工作区干净或选择 stash | `git switch -c <name> [<起点>]` | 切回原分支，`git branch -d <name>`（新分支无新提交） |
| 切换 | 本地或远端存在同名分支 | 本地有则 `git switch <name>`，否则 `git switch --track <remote>/<name>` | 切回原分支 |
| 删除 | 不是当前分支；未合并时列入强确认 | `git branch -d`，未合并且确认后 `-D` | 按快照 `git branch <name> <sha>` 恢复 |

- 部分失败时，结果页顶部显示「2 仓成功、1 仓失败 [回滚成功的 2 仓] [保留]」（IDEA 的同步分支控制同样建议回滚）。
- 选择「先 stash，执行后恢复」时，恢复冲突的仓转入冲突流程，不自动丢弃。

### 4.5 跨仓提交（F06）

- 提交视图顶部切换「单仓 / 工作区」。工作区模式下按仓分组列出所有有改动的仓，勾选文件或块（暂存规则与单仓一致）。
- 一条提交信息，按钮显示「提交到 3 个仓库」；逐仓执行 `git commit`，各仓钩子独立运行。
- 结果逐仓显示：成功（新 SHA）、钩子失败（原始输出）、无暂存内容（跳过）。
- 跨仓提交不是原子操作。部分失败时，已成功的仓保留提交，结果页提供「撤销这些提交」，只对未推送的提交执行 `git reset --soft HEAD~1`，改动回到暂存区。
- Gerrit 仓各自生成 Change-Id，同一卡片的多仓提交在推送时用相同 topic 关联（EP08-F03）。

### 4.6 更新工作区（F07）

```text
+-- 更新工作区 -------------------------------------------+
| 范围      (*) 全部 52 仓   ( ) 选中的 6 仓               |
| 方式      (*) 仅快进 ff-only   ( ) merge   ( ) rebase    |
| 有改动时  (*) 跳过该仓   ( ) 先 stash，更新后恢复         |
+--------------------------------------------------------+
| 预检：将更新 47 仓，跳过 5 仓（3 仓有改动、2 仓无上游）  |
|                                  [取消]   [更新 ⇧⌘U]     |
+--------------------------------------------------------+
```

- 执行顺序：每仓先 fetch，再按方式 pull；ff-only 遇到分叉时该仓标记「已分叉，未更新」，不自动合并。
- 完成后给出汇总：「本次新增 37 个提交，涉及 12 仓 [在时间线查看]」，时间线按每仓更新前后的 SHA 区间过滤（IDEA Update Info）。
- merge / rebase 产生冲突的仓转入 F10 冲突中心。

### 4.7 跨仓 tag 与分支对比（F08、F09）

- 跨仓 tag：输入 tag 名、类型（轻量 / 附注）、目标（各仓当前 HEAD 或指定分支）、「同时推送」；预检重名，推送走 F02 确认。
- 跨仓分支对比：选择分支 A 与 B（如 `release/22.14` 与 `master`），结果表每仓一行：

| 仓库 | A 有 B 没有 | B 有 A 没有 | 说明 |
|---|---|---|---|
| GdThread | 0 | 5 | 点击查看 `git log --oneline A..B` |
| GdHome | 2 | 0 | |
| GdIM | 无 | 无 | A 不存在 |

- 发版前核对用法：A = 发版分支，B = 主干，筛出「主干有修复、发版分支没有」的仓，可直接进入 EP06-F06 跨仓 cherry-pick。

### 4.8 冲突中心与跨仓 stash（F10、F11）

- 冲突中心按仓列出冲突文件数与进行中的操作（merge / rebase / cherry-pick），每行提供「去解决」与「中止」；全部解决前顶部常驻横幅（MRD 10.6）。
- 跨仓 stash：同一描述在多仓执行 `git stash push -m <描述>`；恢复时按描述在各仓查找对应条目执行 `pop`，找不到或冲突的仓单独标记。

## 5. 验收口径

1. 每个多仓动作的逐仓结果与在命令行对该仓逐条执行相同命令一致（沿用 MRD 10.4-9 的抽样比对方法，抽 10 仓）。
2. 推送确认中的仓库与提交数与 `git rev-list --count @{u}..HEAD` 一致；推送后 `git rev-list --count @{u}..HEAD` 为 0（MRD 10.4-13）。
3. 同步分支回滚后，各仓当前分支与分支指针和操作前快照一致（以 `git reflog` 与 `git for-each-ref` 校验）。
4. 跨仓提交后，每个成功仓 HEAD 前进 1 个提交，提交内容等于提交前的 `git diff --cached`。
5. 更新工作区在 ff-only 模式下，任何仓都不产生 merge 提交；有改动且选择跳过的仓工作区不变。
6. 全流程不出现 `push --force`、`--force-with-lease`、无确认的 `reset --hard`（操作日志与 `git reflog` 交叉校验）。

## 6. 风险与明确不做

- 跨仓操作都不是原子的，界面必须如实展示部分成功，并提供回滚或撤销，不做「看似整体成功」的汇总。
- 50 仓并发写操作会给自建 Gerrit 带来压力，并发上限沿用设置（MRD 17.2-7 待定）。
- 批量 push 一次确认还是逐仓确认，沿用 MRD 17.2-6 待定项；本文默认一次确认、可展开逐仓查看。
