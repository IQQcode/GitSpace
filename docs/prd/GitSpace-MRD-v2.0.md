## 1. 产品概述与愿景

GitSpace 是一款面向组件化, 微服务, 多仓库(multi-repo)工程的 macOS 桌面端 Git 可视化客户端。它把分散在多个独立 Git 仓库里的提交, 分支, 改动汇聚进一个统一窗口, 让开发者像看单个仓库一样掌控整个工程全局。

**产品内核**: 对标并强化 IntelliJ IDEA / Android Studio 的"多 VCS root 合并 Log"能力, 把多个独立仓库的提交合并成一条按时间排序的时间线。

**产品手感**: 参考 Fork 的轻量交互——原生 macOS 质感, 克制的信息密度, 右键与快捷键即达, 不要求使用者精通命令行。

**产品底线**: 开源, 免费且可商用, 支持任意私有仓库(含自建 Gerrit), 轻量独立, 不绑定任何 IDE 或编程语言, 首发 macOS。

**本期形态(P0)**: 完整的 macOS Git 客户端——多仓纳管, 跨仓时间线, 同步, 提交, 分支, 合并与冲突处理, 并在其上叠加批量与聚合。P0 的判定线是"日常上班不出这个窗口"(见 10.1, 10.8)。

> 措辞校准(AI 补充): "复刻"改为"能力对标 + 独立实现", 许可与商标边界见 6.4; 其余章节保留原表述以便对照。

### 愿景

让"多仓库"不再成为开发者的认知负担。无论工程被拆成 3 个还是 50 个仓库, 开发者都能在一个视图里看清全局, 完成跨仓的提交核对, 状态体检与批量操作。

## 2. 问题背景

近十年, 组件化与微服务架构成为中大型工程的主流拆分方式, 一个产品的代码往往被拆分到几十个独立 Git 仓库中:

- **移动端大型客户端**: 以抖音客户端 iOS 工程为例, 主壳工程 `app` 之下的 `components/` 目录挂着 50 余个独立组件仓(GdThread, GdPersonal, GdFeedSupports, GdIM, GdHome 等), 每个都是独立 Git 仓库, 通过 mgit / repo 一类多仓工具统一拉取与编译。
- **后端微服务**: 每个服务一个仓库, 一个特性常常横跨后端, 前端, 共享库等多个仓库。
- **多仓协作团队**: 使用 Google repo, meta, mani, mgit 等工具管理成组仓库。

Git 本身以"单仓库"为基本工作单元, 每个仓库的历史相互独立。这带来一个结构性错配: **架构是多仓的, 但绝大多数 Git 工具的视角是单仓的。**

行业调研也印证了多仓模式的治理难点(来源: ThoughtWorks, CircleCI, avivcarmi 等多仓/微服务架构分析):

- 系统知识分散在不同团队维护的多个仓库中, 容易"没有人清楚整个系统如何构建与发布"。
- 跨仓依赖与版本协同需要额外的管理策略, 否则产生团队间摩擦。
- 随着仓库数量增长, 跨仓的提交追踪, 状态核对, 批量操作成本显著上升。

## 3. 问题痛点

把痛点落到真实工作流: 开发者修一个 bug, 同时改了 GdThread, GdFeedSupports, GdHome 三个仓库并各自提交, 想在一个地方确认"这次改动涉及的三仓提交是否都齐了", 现状却是:

- **痛点一: 主流图形客户端是单仓视角。** SourceTree, Fork, Tower, GitHub Desktop, GitUp, Git Cola 等一次只能看一个仓库的历史。即便 Fork 提供了多仓库标签页与 Workspaces(工作区), 它们本质是"快速切换"与"命名会话", 每个标签/会话仍只呈现单仓视图, 跨仓核对依然要在窗口间反复切换, 一个个找, 无法把多仓提交放到同一条时间线。
- **痛点二: 唯一能"多仓合并时间线"的是重型 IDE。** IntelliJ IDEA / Android Studio 能把多个 Git root 合并进统一 Log, 但为了看 git 而常驻一个 IDE 偏重, 且用它打开非本语言工程(如用 Android Studio 看 iOS 仓)体验别扭。
- **痛点三: 体验好的商业 GUI 对公司商用收费。** GitKraken 的 Workspaces 与 GitLens 的提交图在私有仓库上属付费项; SmartGit 仅对个人/开源/非商业免费, 商用按用户订阅(官网 $5/用户/月起); Fork 以免费评估引流, 长期使用需购买授权(单许可证 $59.99, 1 用户至多 3 台设备)。企业内自建 Git 平台(如 Gerrit)场景无法免费长期使用。
- **痛点四: 命令行多仓工具门槛高。** mani, gita, mgit, 自写脚本免费灵活, 但没有图形界面, 对非重度命令行用户不友好, 团队内难以统一推广。
- **痛点五: 多仓同步是体力活。** 50 个仓库开工前要逐个 fetch / pull, Fork 与 SourceTree 一次只能对一个仓库执行, 点 50 次才能确认全都更新; 换成脚本(mgit / 自写)又看不到逐仓结果与失败原因, 出了问题还得回到命令行排查。

**核心矛盾(市场空白)**:

| 维度 | 单仓 GUI(SourceTree/Fork) | 重型 IDE(IDEA/AS) | 商业多仓 GUI(GitKraken 等) | 命令行(mani/gita) | **期望** |
|---|---|---|---|---|---|
| 多仓合并时间线 | 不支持 | 支持 | 支持 | 文本可拼 | **支持** |
| 免费可商用 | SourceTree 是 / Fork 否 | 是 | 否 | 是 | **是** |
| 私有仓库 | 是(SourceTree) | 是 | 付费 | 是 | **是** |
| 图形化低门槛 | 是 | 中 | 是 | 否 | **是** |
| 轻量独立 | 是 | 否 | 中 | 是 | **是** |

"免费可商用 + 图形化 + 多仓合并 + 轻量"这四项同时满足的产品, 当前市场基本空缺。这正是 GitSpace 的立足点。

## 4. 问题诉求

把上述痛点转化为明确的产品诉求:

1. **跨仓统一时间线**: 把工作区内所有仓库的提交合并成一条可过滤(按仓库, 分支, 作者, 时间, 提交信息)的时间线, 一眼看清"这段时间谁在哪些仓库提交了什么"。
2. **轻量高效交互**: 原生 macOS 质感, 启动快, 操作顺, 右键与快捷键即达常用动作, 不要求使用者精通命令行。
3. **开源且免费可商用, 支持私有仓库**: 对企业私有仓库(含自建 Gerrit)零授权成本, 不做免费评估式限购, 代码可审计。
4. **轻量独立**: 占用低, 不绑定 IDE 与编程语言, 纯粹服务于 Git 多仓工作流, 首发 macOS。
5. **跨仓聚合与批量**: 按提交信息/卡片号/作者跨仓聚合检索; 对一组仓库一键批量 fetch / pull / push, 逐仓反馈结果——单仓操作对齐 Fork 的手感, 批量能力是 Fork 不具备的。

## 5. 目标用户与市场

**目标用户画像**:

- 【主】组件化移动端团队(iOS / Android), 工程被拆成几十个组件仓。
- 【主】后端微服务团队, 一个特性横跨多个服务仓库。
- 【次】使用 mgit / Google repo / meta / mani 管理成组仓库的团队。
- 【次】偏好图形化, 用过 Fork/SourceTree 这类轻量客户端但苦于单仓视角或付费墙, 又不愿为看 git 常驻重型 IDE 的 macOS 开发者。

**锚点客户**: 抖音客户端团队(iOS / Android), `app` + `components/` 50 余子仓, 作为首批真实验证场景与种子用户。全篇示例(组件仓, 卡片号, 工作流)统一以此团队为基准, 不再混用其他组织。触达路径见 17.2。

**非目标用户(本期, AI 补充)**:

- 单仓项目开发者(用 Fork / SourceTree 已可满足, 不是本产品的最优场景)。
- Windows / Linux 用户(本期不承诺)。
- 需要代码评审(PR/MR)闭环的团队(本期不做评审服务与评论)。

**市场机会**: 填补"免费可商用的图形化多仓客户端"这一空白。SourceTree 免费且装机量大但功能迭代基本停滞(最新 Mac 版 4.2.12, 近年以安全修复为主); Fork 交互与口碑俱佳(Slant macOS Git 客户端排名第 3, Product Hunt 4.9/5)且更新活跃(Fork 2.71, 2026-10), 却是 $59.99 买断收费且单仓视角; GitSpace 以"Fork 级手感 + IDEA 的多仓内核 + 开源免费"切入这块未被满足的需求。

> 补充(AI): 可服务规模尚未量化(内部组件化团队人数, 外部潜在用户数), 建议 P0 PRD 阶段补一个量级假设, 否则"市场机会"只能是定性判断。

## 6. 标杆能力分析: IntelliJ IDEA Community 的图形化多仓合并

GitSpace 的能力内核直接对标 IntelliJ IDEA Community(以及同内核的 Android Studio)的版本控制功能。

### 6.1 核心功能

- **多 VCS root 注册(Directory Mappings)**: 在 Settings > Version Control > Directory Mappings 中, 把工程下的多个 Git 仓库目录逐个注册为 VCS root; 打开包含多个 `.git` 的目录时, IDE 会自动检测并提示一键注册所有未登记的仓库。
- **统一 Log 视图**: Git 工具窗口的 Log 标签把所有已注册 root 的提交合并显示为一条按时间排序的时间线, 并绘制跨仓的提交图。
- **强大的过滤**: 顶部支持按 Branch(分支), User(作者), Date(时间), Path(路径)过滤, 左侧 Branches 面板列出所有本地与远程分支, 可开多个 Log 标签并存不同过滤条件。
- **语言无关**: Log 视图只读取 Git 元数据, 与工程使用何种编程语言无关, 用它查看任意多仓工程都成立。
- **免费可商用**: IntelliJ IDEA Community 基于 Apache 2.0 许可, 企业商用同样免费, 对私有仓库无任何限制。

### 6.2 为什么它是最佳基底

- **"多仓合并时间线"在免费可商用产品里几乎独一份**, 这是 GitSpace 最核心, 最难被竞品复制的价值点。
- **自动检测 + 手动登记的双通道**, 兼顾"打开即用"与"精确控制"。
- **过滤能力成熟**, 直接对应"按作者/时间/仓库快速定位跨仓改动"的真实诉求。

### 6.3 作为基底的改造方向

IDEA 的多仓能力附着在重型 IDE 之上, GitSpace 要做的是: 把这套"多仓合并内核"抽取为独立, 轻量的专用客户端, 并在其上叠加更贴合多仓场景的能力(见第 10 章), 例如"同一逻辑变更跨多仓的提交聚合"这类 IDEA 尚未直接提供的视图。

### 6.4 对标边界(许可与表述, AI 补充)

"对标"指能力与交互范式对标, 不复制代码与素材。IntelliJ IDEA Community 采用 Apache 2.0 许可, 商用无授权成本, 但:

- 若后续参考或复用其源码, 需保留 NOTICE 与许可声明, 并做一次许可证审查(尤其涉及第三方组件与图标资源)。
- 若仅以公开文档与产品行为为参照, 对外表述建议使用"能力对标 / 独立实现", 避免"复刻"引发的许可与商标联想。

## 7. 交互与视觉参考: Fork 的优点与短板

GitSpace 的交互手感对标 Fork(独立开发者 Dan Pristupov 与 Tanya Pristupova 出品的 Git 客户端, 官网定位语 "A fast and friendly git client for Mac and Windows")。以下基于 2026-10 对 git-fork.com 的实站调研与第三方评测。

### 7.1 Fork 基本盘(调研事实)

- **平台与形态**: macOS(OS X 10.11+)与 Windows(7+)原生客户端, 无 Linux 版; Mac 端为 Swift/Cocoa 原生实现, 界面质感与系统一致。
- **定价**: 免费评估 + $59.99 买断, 1 个许可证供 1 名用户在至多 3 台设备(Mac/Windows 通用)使用, 商用需购买。
- **维护活跃**: 更新频繁, Fork 2.71(2026-10-23)仍在新功能迭代; 近期版本已加入 Workspaces(按窗口的工作区/命名会话), Vertical tabs, AI agent 生成提交信息(Cursor), worktree 支持等。
- **口碑**: Product Hunt 全时段 4.9/5; Slant "最佳 macOS Git 客户端"排名第 3, "最佳 Windows Git 客户端"排名第 2; Homebrew 安装热度高。

> 核验记录(2026-10-29): 以上四条与官网及 Release Notes 一致。注意两点: ① Slant 页面展示的 $49.99 为历史价格, 引用价格时以官网 $59.99 为准; ② Product Hunt 4.9/5 基于 34 条评价, 样本量小, 仅作定性参考。

### 7.2 值得借鉴的交互优点

- **多仓库标签页**: 一次可同时打开多个仓库, 各占一个标签页, 标签上以 `*` 与红点标注未提交改动, 快捷切换不丢上下文。
- **顺滑的行级暂存**: stage / unstage 可按行操作, 且不会像 SourceTree 那样在每次暂存后把文件滚动位置重置回顶部——组合提交体验明显更好。
- **可视化交互式 rebase**: 以图形列表编辑, 重排, squash 提交。
- **冲突助手与内置冲突解决器**: 直观的冲突定位与三方合并入口。
- **成熟的 diff 体验**: 行内差异高亮, 并排/统一视图, 常见图片格式的 diff, Blame 与按文件/目录的 History 视图。
- **常用 Git 能力图形化全覆盖**: fetch/pull/push, commit/amend, 分支与 tag, cherry-pick/revert, merge/rebase, stash(直接显示在提交列表), submodule, Reflog 恢复丢失提交, git-flow, Git LFS, GPG。
- **键盘优先**: 快捷键组织合理, 配合顶部 Quick Launch 与仓库内 Filter 搜索, 全程少用鼠标。
- **细节状态提示**: 有未提交改动的仓库名带 `*`, GitHub 通知轻量不打扰。

### 7.3 视觉风格调研(官网与客户端)

**官网(git-fork.com)风格——GitSpace 官网与品牌物料可参考**:

- 浅色极简路线: 纯白底 `#FFFFFF` 与浅灰 `#F9F9F9` 分区交替, 大量留白。
- 品牌主色为明快的 Fork 蓝 `#1BA3EF`(主按钮/CTA), 链接蓝 `#007BFF`, 正文深灰 `#212529`。
- 字体为系统栈(-apple-system/system-ui), 标题与按钮使用细字重(light/300), 大字号居中标题, 整体轻盈克制。
- 轻拟物点缀: 卡通小鸟吉祥物, 柔和自然风景背景与真实应用截图叠放, 传达"快而友好"。

**客户端 UI 风格——GitSpace 交互与视觉基准**:

- 原生 macOS 窗口与控件, 默认以深色主题示人, 明暗主题均需支持。
- 顶部工具栏: Quick Launch, Fetch/Pull/Push/Stash, 当前分支切换, New Branch, Open in Terminal, Feedback 一字排开, 高频操作一步直达。
- 顶部仓库标签行 + 左侧仓库信息侧栏(收藏/Stared, 本地分支树, Remotes, 顶部 Filter 框), "All Commits / Local Changes" 双视图切换。
- 提交列表以多彩提交图(branch graph 彩色曲线)呈现, 行内含头像, 短 SHA, 日期时间, 选中行高亮; 提交详情面板按 Author/Committer, Refs, SHA, Parents 与变更文件树组织。
- Diff 视图行内红绿高亮, 支持并排对比; 空态/加载态克制, 视觉噪音低。

> 视觉边界(AI 补充): 以上只作为风格基准。品牌与界面不复用 Fork 的图标, 插画, 配色方案与截图, 避免与既有产品产生视觉混淆(见第 14 章法务)。

### 7.4 明显短板(GitSpace 要补齐的)

- **无跨仓合并视图**: 标签页与 Workspaces 只是"多开的会话", 每个标签仍只渲染单仓的提交列表, 不存在把多仓提交合并为一条时间线的视图。这正是 GitSpace 的核心缺口补位。
- **买断收费**: $59.99/许可证, 免费评估到期后商用必须购买, 企业批量分发成本高。
- **无 Linux 版本**(且本次定位下 GitSpace 首发也只承诺 macOS, 双方在 Windows/Linux 的差距留待后续路线图再评估)。
- **多仓批量能力薄弱**: Workspaces 面向"切换", 不面向"对一组仓库批量 pull/体检/按卡片号聚合检索"。

### 7.5 GitSpace 的取舍

P0 取 Fork 的视觉基准, 交互节奏(标签页, 快捷键, 紧凑信息密度)与日常写操作能力(提交 / 分支 / 合并); 冲突解决先走"列表 + 选边 + 外部工具", 内置合并器留到后续; 补上它最大的缺口——跨仓统一时间线与多仓批量; 并以"开源 + 免费可商用"替代它的付费墙。SourceTree 的"书签式纳管"思想仍保留在"工作区 + 仓库列表"中, 但不再是交互标杆。

| SmartGit | 仓库分组(非合并) | **否(仅非商业免费, 商用 $5/用户/月起)** | 否 | 是 | 是 | 中 | 全 | 中 |
| Fork(交互标杆) | 否(标签页/Workspaces 为命名会话) | **否($59.99 买断)** | 否 | 是 | **是** | **是** | Mac/Win | **高** |
| GitButler | 否(多窗口开多仓, 非合并) | 是 | 否(部分开源) | 是 | 是 | 是 | Win/Mac/Linux | **高(新锐)** |

**结论**: 现有产品在"多仓合并 + 免费可商用 + 图形 + 轻量"四项上均存在缺失——交互最好的 Fork 缺多仓合并且收费, 免费的 SourceTree 单仓且停滞, 多仓合并的 IDEA 偏重, GitKraken 收费。GitSpace 的差异化空位清晰: 做那个"同时满足四项"的产品。

**风险视角(AI 补充)**: 补全竞品后结论不变, 但威胁排序变化——最需要盯的不是 Fork, 而是 ① Fork 的 Workspaces 是否演进为真合并视图(它已有数据模型与用户心智); ② 免费阵营的 GitButler(迭代极快, 已覆盖完整 Git 客户端能力, 一旦加入多仓合并, 差异化窗口立即收窄); ③ Tower / Sublime Merge 属成熟付费阵营, 短期不会下探免费。GitSpace 的额外差异点是"开源可审计", 这是商业产品无法对标的一项。

## 9. 产品定位与核心价值

**一句话定位**: IDEA 的多仓合并内核 × Fork 的轻量交互手感 × 开源免费可商用 × 轻量独立(macOS 首发)。

**核心价值主张**: 让开发者在一个人人免费可用的 macOS 窗口里, 像管理单个仓库一样管理几十个仓库。

**差异化(为什么不是又一个 Git 客户端)**:

- 免费阵营(SourceTree, GitHub Desktop)停留在单仓且交互停滞; 手感最好的 Fork 收费且多仓仍是"切换"而非"合并"; 多仓合并能力要么藏在重型 IDE 里, 要么对企业收费。GitSpace 把"多仓合并"这件只有 IDE 能做好的事, 做成一个人人可免费商用的独立轻量工具。
- 面向"多仓工作流"本身做产品(统一时间线, 多仓体检, 卡片号聚合), 而不是把多仓当作单仓功能的附属。

**路线选择(已决策, 2026-10-29, 二次修订)**:

- **路线一 替代型(选定)**: 完整 Git 客户端——日常闭环(拉取 / 提交 / 推送 / 分支 / 合并 / 冲突)对齐 IDEA 与 Fork, 以"跨仓聚合 + 批量 + 免费开源"做差异化。与 Fork 正面竞争, 不要求用户同时开两个工具。
- **路线二 补位型(放弃)**: 只做跨仓聚合与同步, 写操作跳转外部工具。放弃原因: 拉完还得切窗口才能提交, 割裂感强; 用户既已把 Fork 当基准, 半个客户端不会被接受。
- **代价与前提**: 正面竞争意味着单仓体验不能明显弱于 Fork(手感, 快捷键, 稳定性, 边界场景), 工期与质量门槛显著上升(见 13, 14)。

## 10. 核心功能需求

**范围决策(2026-10-29, 二次修订)**: P0 覆盖"日常 Git 闭环"——拉取, 提交, 推送, 分支, 合并, 冲突处理, 以及多仓工作区上的聚合与批量; 与 IDEA / Fork 的基本能力对齐(见 10.1)。差异化不在单仓功能的数量, 而在"跨仓统一视图 + 批量 + 免费开源"; 分期只用于排期, 不用于削减 P0 承诺。

### 10.2 P0 功能清单(日常闭环)

**A. 工作区与视角**

- 多仓工作区: 手动添加 / 父目录扫描(50+ 仓) / 配置本地保存与恢复 / 多工作区切换。
- 跨仓统一时间线与单仓视图切换; 过滤(仓库 / 分支 / 作者 / 时间 / 关键字); 提交详情与 diff(统一 / 并排); blame 与文件历史。

**B. 同步(单仓 + 批量)**

- fetch / pull / push: 单仓, 选中多仓, 全部仓库; 并行执行(默认并发 4, 可调 1–8)。
- pull 双模式: 默认 ff-only(安全); 可选 merge(产生冲突则进入 10.2-E 的冲突流程); rebase 模式 P1。
- push: 仅对已配置上游的分支; 执行前展示将推送的仓库与提交数; 被拒(非快进)不自动合并; 永不 force。
- 批量面板: 逐仓 排队 / 执行 / 成功 / 跳过 / 失败 + 原因, 可取消, 单仓重试, 失败项一键重跑。

**C. 提交链路**

- 改动视图: 未暂存 / 已暂存 两栏, 文件树 + 列表, 双击看 diff。
- 暂存粒度: 文件级与块级(hunk); 实现为 `git diff` 拆块后 `git apply --cached`, 结果须与 `git add -p` 等价。
- 丢弃改动: 单文件 / 单块 / 全部, 二次确认, 支持撤销(基于操作前快照)。
- 提交: message 输入(历史建议, 上次信息, 模板占位), amend, 提交后刷新暂存区与时间线。
- 钩子: 支持 pre-commit / commit-msg, 失败时展示钩子原始输出, 不吞错, 不产生提交。
- 空提交 / 无可提交内容 / detached HEAD 下给出明确提示, 不静默失败。

**D. 分支**

- 本地与远程分支列表, 当前分支标识, upstream 关联与显示。
- 创建(基于当前 HEAD 或指定提交), 切换(有未提交改动时提示 stash 或取消), 删除(未合并需强确认), 重命名。
- 检出远程分支为本地分支, 并设置 upstream。

**E. 合并与冲突**

- merge: 快进与非快进; 非快进的 merge commit message 可编辑; 完成后提示是否立即 push。
- 冲突: 冲突文件列表(与 `git status` 完全一致), 每文件标记 未解决 / 已解决; 支持"取当前(ours)", "取对方(theirs)", "两者都保留", 或"用外部合并工具打开"(FileMerge / Kaleidoscope / VS Code, 可配置)。
- 收尾: 全部标记已解决才允许提交; 随时可"中止合并"(`merge --abort`), 工作区回到合并前。
- 不做三方自动合并算法: 冲突内容交给 git 与外部工具, 产品只负责定位, 选边, 收尾。

**F. stash 与 tag**

- stash: 保存(带 message), 列表, 查看 diff, pop / apply / drop。
- tag: 创建(轻量 / 附注), 列表, 删除, 推送。

**G. 安全边界(硬约束)**

- 不提供 force push; 不提供无确认的 `reset --hard` / `clean -fd`。
- 破坏性操作(丢弃改动, 删除未合并分支, 中止合并)一律二次确认并说明影响范围。
- 中断或崩溃后仓库不处于半完成状态: 可继续, 可中止, 状态可解释。
- 所有写操作写本地日志(时间, 仓库, 操作, 结果), 可回溯。

### 10.3 P1 / P2(补齐与差异化)

**P1(补齐高级单仓能力)**

- 行级暂存; 非交互 rebase; cherry-pick / revert; 图片 diff。
- 跨仓聚合检索(按提交信息 / 作者 / 卡片号, 复制交付清单)。
- 工作区自动刷新; 提交模板与卡片号联动。

**P2(差异化与平台)**

- 交互式 rebase; 变更集(ChangeSet)视图; 团队工作区共享; submodule / worktree 管理。
- Windows / Linux 扩展评估。

### 10.4 P0 验收标准

1. **多仓纳管**: 指定含 50+ Git 仓库的父目录, 首次冷扫描在 60s 内完成登记(口径: 50 仓 × 平均 5 万提交, 无缓存); 增量刷新 ≤5s; 重启后工作区自动恢复。
2. **时间线性能**: 50 仓 × 10 万提交下, 首屏(≥100 条)渲染 ≤3s, 过滤响应 ≤300ms, 滚动平均 ≥55fps, 常驻内存 ≤500MB(基准 M1 / 16GB)。
3. **状态准确性**: 抽 20 仓 × 4 类状态(当前分支, 领先/落后, 未提交, 未推送), 与 `git status --porcelain` 及 `git rev-list --count` 全部一致; 同时展示数据截至的 fetch 时间。
4. **数据安全**:
   - 只读操作与 fetch 前后, 工作区与暂存区不变(`git status --porcelain` 一致, 未提交文件内容哈希不变)。
   - 本地分支指针仅在 pull 快进, merge, commit, 切分支时按语义变化, 无隐式移动。
   - 全流程不出现 `push --force` / 无确认的 `reset --hard` / `clean -fd`(操作日志与 `git reflog` 交叉校验)。
5. **私有仓库兼容**: HTTPS 与 SSH 两种鉴权, 在 GitHub / GitLab / 自建 Gerrit 上完成"浏览 + fetch + pull + commit + push + 合并"全流程; 企业代理与自签证书可用。
6. **轻量**: 冷启动 ≤2s(50 仓工作区), 空载常驻内存 ≤200MB, 安装包 ≤60MB(Apple Silicon)。
7. **稳定性**: 会话崩溃率 <0.5%; 单仓读取失败不阻塞其他仓库, 有明确提示与重试入口。
8. **零门槛**: 无登录, 无许可证, 无试用期限制; 全部 P0 功能对商业使用无功能阉割(见第 12 章开源许可)。
9. **批量同步准确性**: 50 仓批量 fetch / pull 的逐仓结果与命令行逐条执行一致(抽 10 仓比对); 单仓失败不影响其余, 失败原因可读。
10. **提交链路**: 文件级 / 块级暂存结果与 `git add -p` 一致(同一份改动逐块比对 `git diff --cached`); 提交后 HEAD 前进 1 个提交且工作区干净; amend 后父提交不变; pre-commit 钩子失败时提交不产生且展示原始输出。
11. **分支**: 有未提交改动时切换分支必须阻止或引导 stash, 不得静默丢弃; 删除未合并分支需强确认, 取消后分支仍在; 检出远程分支后 upstream 关联正确。
12. **合并与冲突**: 冲突列表与 `git status --porcelain` 完全一致; 选 ours / theirs 后文件内容与 `git checkout --ours / --theirs` 结果一致; 未全部解决时不允许提交; 中止合并后 HEAD 与工作区恢复到合并前(`git reflog` + `git status` 校验)。
13. **push 安全**: 非快进被拒不自动 merge, 不 force; 确认弹窗展示的仓库与提交数与实际一致; 对自建 Gerrit 的推送遵循仓库现有 remote 配置。

### 10.5 功能边界

**本期不做**: 代码托管 / 评审服务端; 云端同步与账号体系; PR / MR 创建与评论; 非 Git 的其他 VCS; LFS 大文件托管; submodule 递归操作(P2); 三方自动合并算法; Windows / Linux(本期)。

**不应该生效的场景**: 未纳管目录不参与时间线与状态统计; bare 仓库与 detached HEAD 下不提供分支切换与合并入口(只读 + fetch); 无写权限或鉴权失败的远端不进入批量写操作; 只读文件系统上的仓库标记为"仅浏览"。

### 10.6 关键流程与状态(AI 补充, 待确认)

**流程一: 父目录扫描纳管**

1. 点击"添加仓库 → 扫描父目录", 选择工程根目录。
2. 递归发现仓库(`.git` 目录; separate-git-dir 与 submodule 的判定规则待定), 列表预览路径, 当前分支, 最近提交时间。
3. 勾选后确认导入, 工作区配置写入本地。
4. 时间线按仓库并行加载元数据, 已就绪的仓库先渲染, 未就绪显示占位。

**流程二: 跨仓核对(核心路径)**

1. 打开工作区, 默认进入统一时间线。
2. 按作者 / 时间 / 关键字 / 仓库过滤。
3. 点击任一提交, 右侧查看详情与文件 diff。
4. 结束状态: 确认"N 个仓库的改动均已提交", 可一键复制提交清单(SHA + 仓库 + 标题)。

**流程三: 发版体检**

1. 切到状态总览, 按"未推送 / 有未提交 / 落后于远程"排序。
2. 逐仓查看差异; 需要处理时就地 pull / push, 或跳转外部工具。
3. 结束状态: 全部仓库状态符合预期, 列表无异常标记。

**流程四: 开工 / 发版批量同步**

1. 状态总览勾选仓库(或全选), 点击 Fetch / Pull / Push。
2. 预检: 逐仓检查鉴权可达, 上游配置, 未提交改动, 是否可快进; 输出"将执行 N 仓, 跳过 M 仓(原因)"。
3. 确认后并行执行, 逐仓刷新状态。
4. 结束状态: 每仓都有明确结果, 可重试失败项, 或跳转外部工具处理需人工的仓库。

**流程五: 提交**

1. 改动视图列出 N 个未暂存文件, 逐个查看 diff。
2. 选择文件或块加入暂存区(两栏实时更新)。
3. 填写提交信息(可从历史 / 模板补全), 必要时勾选 amend。
4. 提交; 钩子执行; 成功后清空暂存区并刷新时间线。
5. 结束状态: 工作区干净, 时间线顶部出现新提交, 可一键 push。

**流程六: 分支合并**

1. 切到目标分支, 选择要合并的来源分支(本地或远程)。
2. 执行 merge; 快进直接完成, 非快进生成 merge 提交(信息可编辑)。
3. 若冲突, 进入冲突列表: 逐文件选择 ours / theirs / 两者, 或用外部工具处理, 标记已解决。
4. 全部解决后提交合并; 或随时中止, 回到合并前。
5. 结束状态: 合并完成并可立即 push; 或已中止且工作区干净。

**状态与异常表现**:

| 场景 | 期望表现 |
|---|---|
| 首次加载 / 切换工作区 | 骨架屏 + 进度("已加载 12/50 仓库"), 已就绪部分先渲染 |
| 空工作区 | 空态说明 + "添加仓库 / 扫描目录"主按钮 |
| 筛选无结果 | "没有匹配的提交" + 一键重置筛选 |
| 单仓读取失败(权限/损坏) | 该仓标记异常, 不阻塞其他仓库, 提供"重试 / 移除" |
| 超大仓(>20 万提交) | 默认只加载近 3 个月(可调), 顶部提示"已按时间窗口截断" |
| remote ref 过期 | 状态区标注"数据截至 X 小时前", 提供 fetch 入口 |
| 合并冲突中 | 顶部常驻"合并进行中"条, 冲突面板置顶, 提供"中止合并" |
| 分支切换被未提交改动阻塞 | 弹窗选择: stash 后切换 / 取消 |
| 钩子失败 | 展示原始输出与常见原因, 提交未产生, 工作区保持改动 |
| 批量操作中途取消 | 已完成仓保留结果, 未开始仓标记"已取消", 不回滚已完成项 |
| pull 遇到分叉 | 按所选模式处理(ff-only 跳过 / merge 进入冲突流程), 并标注原因 |
| push 被拒(非快进) | 提示"远端有新提交, 请先 pull", 不自动合并, 不 force |
| 鉴权失败(SSH key / token) | 提示具体仓库与失败原因, 提供凭据配置入口 |

### 10.7 成功指标与衡量方式(AI 补充)

**北极星指标**: 周活跃"跨仓核对 + 跨仓同步"开发者数——一周内至少完成一次跨仓核对或批量同步的开发者数。理由: 它同时衡量"聚合价值"与"工具的日常可用性"。

| 指标 | 定义 | 首版 3 个月目标 | 测量方式 |
|---|---|---|---|
| 激活 | 安装后 7 天内建立 ≥10 仓工作区 | ≥ 60% | 匿名埋点 |
| 留存 | 次周仍打开的开发者占比 | ≥ 50% | 匿名埋点 |
| 日常闭环 | 一周内同时用过"同步 + 提交 + 分支"的开发者占比 | ≥ 40% | 匿名埋点 |
| 效率 | 一次跨仓核对耗时(vs 命令行 / 多开 GUI 基线) | 下降 ≥ 50% | 基线计时 + 用户自报 |
| 覆盖 | 锚点团队日常使用人数占比 | ≥ 30% | 内部调研 |
| 可靠性 | 批量同步与提交的逐次成功率, 按失败原因分布 | ≥ 99% | 本地操作日志(匿名聚合) |
| 替代度 | 一周内"未打开过其他 Git 客户端"的用户占比 | 监测项 | 问卷 |
| 诉求信号 | 明确提出"行级暂存 / 交互式 rebase"的用户占比 | 监测项 | 反馈渠道 |

### 10.8 与 Fork 的能力对照(对齐什么, 超出什么)

| 能力 | Fork | GitSpace P0 | 说明 |
|---|---|---|---|
| 单仓浏览 / diff / blame | 完整 | 有 | 对齐 |
| fetch / pull / push | 有 | 有(+ 跨仓批量) | 对齐并超出 |
| 提交(文件 / 块级) | 有(行级) | 有(文件 + 块级) | 对齐, 行级 P1 |
| 分支 / merge / 冲突 | 有(内置解析) | 有(列表 + 选边 + 外部工具) | 对齐, 内置合并器 P1–P2 |
| stash / tag | 有 | 有 | 对齐 |
| 多仓标签页 | 有 | 有 | 对齐 |
| 跨仓统一时间线 | 无 | **有** | 超出 |
| 多仓状态总览 | 无 | **有** | 超出 |
| 父目录扫描纳管 50+ 仓 | 无 | **有** | 超出 |
| 卡片号聚合 / 变更集 | 无 | P1 / P2 | 超出 |
| 免费 + 开源可审计 | 收费闭源 | **有** | 超出 |

**一句话**: P0 把单仓日常闭环对齐 Fork, 在多仓聚合与批量上超出; 复杂改写(行级暂存, 交互式 rebase, 内置三方合并)在 P1–P2 继续补齐。

## 11. 典型使用场景

**场景一: 跨仓改动核对(最高频, P0)**
修一个 bug 改了 GdThread, GdFeedSupports, GdHome 并分别提交。打开 GitSpace, 统一时间线上按时间顺序看到三条提交并列, 一眼确认三仓都已提交且信息规范, 不再逐个仓库翻找。

**场景二: 发版前多仓体检(P0)**
版本封板前, 在多仓状态总览里一屏扫出哪些仓库还有未推送提交, 哪些分支不一致, 避免漏提交导致提测缺改动; 数据过期时可在总览里直接 fetch 再刷。

**场景三: 按卡片号聚合交付清单(P1)**
迭代结束, 输入迭代卡片号(示例 `TASK-123456`, 以团队实际编号规则为准), GitSpace 聚合出本次涉及的所有仓库与提交, 直接作为 CR 清单或交付说明的依据。

**场景四: 新人快速建立工程全局(P0)**
新成员加入, 用"扫描父目录"一键纳管团队工程, 一个窗口看清整个组件化工程由哪些仓库组成, 各自状态如何, 快速建立全局认知。

**场景五: 批量同步(P0)**
每日开工, 对工作区所有仓库一键批量 pull, 列表反馈每个仓库的更新结果与冲突提示。

**场景六: 一次改动的完整闭环(P0)**
改完 GdThread 的两个文件, 在改动视图逐块暂存, 写提交信息并 commit, 直接在列表里 push; 另一个仓库的分支需要合入主干, 切到主干 merge, 冲突文件逐个选边收尾。全程不离开 GitSpace。

> 基线说明(AI 补充): 场景一中的"逐个仓库翻找"目前没有实测耗时。建议 M0 期间对锚点团队 5 名开发者做一周计时(每次跨仓核对的起止), 作为 10.7 "效率"指标的分母。

## 12. 非功能需求

- **性能**: 工作区含 50+ 仓库时仍流畅。采用增量读取, 时间线虚拟滚动与懒加载分页, 文件监听排除构建产物(build / DerivedData / Pods)等手段控制资源占用; 量化指标见 10.4。
- **平台**: 首发并专注 macOS(原生质感优先); Windows 与 Linux 在 M4 之后评估, 本期不承诺。
- **仓库托管兼容**: 支持任意 Git 远程, 含 GitHub, GitLab, Bitbucket 及企业自建 Gerrit。
- **分发**: GitHub Releases 提供 dmg 下载 + Homebrew Cask 安装(Fork 在 Homebrew 的高热度证明该渠道对 Mac 开发者有效)。
- **数据与隐私**: 仓库数据与凭据全部本地处理, 不上传云端; 不强制账号。
- **许可与开源**: 以 OSI 认可许可开源发布(建议 Apache 2.0: 含专利授权, 企业商用友好; 亦可选 MIT, 见 17.2), 源码托管 GitHub, 提供贡献指南, Issue 模板与安全披露流程; 发布版本由 GitHub Actions 构建并签名, 可复现。

**安全与凭据**: SSH key 与 HTTPS token 交由 macOS Keychain 管理, 不落明文, 不写日志; 支持 ssh-agent 与已有 `~/.ssh/config`。

**外部工具集成**: 可配置外部合并工具(FileMerge / Kaleidoscope / VS Code 等), 冲突文件一键调用; 可配置在终端 / IDE / 其他 Git 客户端中打开仓库。

**分发与合规**: Developer ID 签名 + 公证(notarization), 否则 Gatekeeper 默认拦截, 首启体验直接失败; 更新走 Sparkle(或等价方案)并校验签名。

**网络与并发**: 批量操作默认并发 4(可配置 1–8), 单仓超时 60s, 仅对网络类错误自动重试 1 次; 支持企业代理与自签证书; 凭据优先读 ssh-agent, 其次 Keychain。

**隐私与统计(已决策: 允许匿名统计)**:

- 默认开启匿名聚合统计, 首次启动明确告知, 设置页可一键关闭, 关闭后完全停止上报。
- 仅上报聚合事件: 启动/退出, 仓库数区间(如 10–49), 功能使用计数(时间线/过滤/状态总览/跳转), 崩溃堆栈。
- **不上报**: 仓库名, 路径, 远程地址, 分支名, 提交信息, 代码内容, 凭据, 用户身份。
- 设备标识为随机 UUID, 可在设置中重置; 事件不含精确时间戳以外的关联信息; 服务端保留 90 天。
- 崩溃日志本地留存可导出, 用户可选择是否随匿名统计上报。

**兼容性**: 最低 macOS 13(Ventura), Apple Silicon 优先, Intel 可用; 依赖系统 git ≥ 2.30 或内置 libgit2 / gitoxide(技术评审决定); 支持企业代理与自签证书。

**国际化与无障碍**: 首版中 / 英双语; 关键路径支持 VoiceOver 与全键盘操作。

**文件监听**: 50+ 仓会触及 FSEvents 上限, 需采用"触发式刷新 + 低频轮询"的折中方案, 具体阈值在 M0 测定。

## 13. 里程碑与路线图(粗略)

- **M0 冻结与预研(2 周)**: 冻结 10.2 范围; 用一次性脚本验证"50 仓元数据读取 + 10 万提交渲染 + 块级暂存"的可行性(不冻结技术栈); 原型 5 人可用性测试; 产出 P0 PRD 与技术评审材料。
- **M1 骨架与同步(6–8 周)**: 纳管(手动 / 扫描), 跨仓时间线, 状态总览, 只读 diff / blame, fetch / pull / push(单仓 + 批量面板)。内部可用, 可交种子用户。
- **M2 日常闭环(6–8 周)**: 暂存(文件 + 块), commit / amend / discard, 分支创建切换删除, stash, tag, 提交历史与模板。此时可替代 Fork 的日常提交。
- **M3 合并与冲突(4–6 周)**: merge(快进 / 非快进), 冲突列表 + 选边 + 外部合并工具, 中止合并, 合并后推送。至此完成"不出窗口的日常闭环"。
- **M4 补齐与差异化(持续)**: 行级暂存, 非交互与交互式 rebase, cherry-pick / revert, 卡片号聚合, 变更集视图, 团队工作区共享。
- **人力与周期(AI 估算, 待研发校准)**: 2 人 → 到 M3 约 4–5.5 个月; 3 人 → 约 3–4 个月。若只能保 1.5 人, 冲突解决维持"列表 + 外部工具"方案(当前设计即按此), 不追加内置合并器。
- **技术选型**: 不在本 MRD 决策范围, 由 P0 PRD 通过后的技术评审确定; 选型必须满足 10.4 的性能指标与第 12 章的轻量约束。
- **时间盒**: 待补充——需明确 M1 的 deadline 与版本卡点。

## 14. 风险与依赖

- **范围风险(最高)**: 路线一意味着与 Fork 正面竞争。Fork 的手感是十年打磨, 首版在快捷键, 状态提示, 撤销与边界场景上必然有差距; 若单仓体验只做到 80%, "多仓聚合"必须足够强才能驱动迁移。缓解: 把跨仓核对 / 批量同步 / 扫描纳管做到明显优于任何替代方案, 同时允许用户用跳转补足单点短板。
- **冲突解决体验风险**: P0 不做内置三方合并器, 只有"列表 + 选边 + 外部工具"。同一区域多侧修改这类复杂冲突仍需离开应用, 这是与 IDEA / Fork 最直观的差距; 若种子用户反馈强烈, 提前在 P1 接入开源合并引擎的图形封装。
- **同步与写操作风险**: 一旦能改仓库, 一次误操作就足以摧毁信任。兜底: 不 force, 破坏性操作二次确认且可中止, 操作日志可回溯; 若失败率 >5%, 优先修稳定性而不是加功能。
- **认知风险**: 用户会拿它与 Fork 逐项对比, "少了 X" 比 "多了 Y" 更容易被感知。市场沟通要突出多仓与免费开源, 但不要回避单仓能力的阶段差距。
- **技术风险**: 原生手感与轻量是硬指标, 但选型延后到技术评审, 存在"选型无法同时满足"的可能。约束不变(10.4 的性能与第 12 章的轻量), 若原生方案工期不可接受, 回退方案为"原生外壳 + Web 渲染核心视图", 但需重新评估启动与滚动指标。
- **技术细节风险**: 50+ 仓的文件监听触及 FSEvents 上限, 需退化为轮询 + 触发式刷新; 单仓 20 万提交的图布局与内存; submodule / worktree / 浅克隆的处理规则; 企业内网代理与自签证书。
- **竞品动态风险**: Fork 迭代非常活跃(Workspaces, Vertical tabs, AI 提交信息), 若其把 Workspaces 升级为真正的合并视图, 差异化窗口将收窄; 免费阵营的 GitButler 迭代同样快。GitSpace 需尽快以"开源 + 多仓合并 + 批量体检"建立用户心智。
- **市场风险**: 用户已有工具习惯(Fork/SourceTree, 命令行)存在迁移成本; 需以"多仓合并"这一刚需差异点驱动迁移。
- **可持续性风险**: 开源后维护依赖作者投入与社区贡献, 无商业收入支撑。需明确三年维护预期, 发布节奏(建议月度补丁 + 季度功能), 以及在停止维护时的交接方式(开源本身降低了锁定风险, 但需提前写好治理说明)。
- **生态依赖**: 依赖底层 Git 能力与各托管平台的鉴权方式, 企业自建平台(Gerrit)的兼容需专门适配。
- **法务**: 产品命名 GitSpace 需做商标检索(可能与既有 SaaS 重名); 开源许可需与依赖库许可兼容(尤其 GUI 框架与 diff 渲染库); 视觉上不复制 Fork 官网/客户端的具体设计元素与素材, 仅作风格基准; 若参考 IDEA 源码需保留 Apache 2.0 NOTICE。

## 15. 附录

**名词表**:

- 多仓库(multi-repo): 一个产品的代码分散在多个相互独立的 Git 仓库中。
- VCS root: 版本控制系统中被登记的一个仓库根目录。
- 统一 Log / 合并时间线: 把多个仓库的提交合并为一条按时间排序的视图。

- remote-tracking ref: 本地记录的远端分支指针(如 `origin/main`), 仅 fetch 后更新; P0 的"领先/落后"基于它计算。

5. **统计后端**: 自建最小化收集端(轻量)还是用现成分析服务(需评估隐私合规与开源项目的可信度)。
6. **push 确认粒度**: 批量 push 一次确认全部, 还是逐仓确认(更安全但更慢)? 这决定误推风险与操作效率的平衡点。
7. **默认并发度**: 批量同步默认并发 4 是否合适(需评估内网镜像与自建 Gerrit 的压力)。
8. **人力配置**: 2 人(到 M3 约 4–5.5 个月)还是 3 人(约 3–4 个月)? 这直接决定能否按期交付日常闭环。
9. **冲突解决深度**: P0 接受"列表 + 选边 + 外部工具", 还是必须内置三方合并编辑器(会把 M3 再推后 4–6 周)?
